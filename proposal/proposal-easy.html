Mini Project — Infra Network Engineer · 우상목

데이터센터 네트워크 제안서.

Kubernetes 클러스터(컨트롤러 3대, 워커 5대)와 Ceph 스토리지 4대를 랙 3개에 넣는 네트워크를 설계했습니다. 장비 목록부터 늘어놓기보다 데이터가 실제로 어떤 길로 다니는지를 먼저 보여 드리고, 왜 그렇게 만들었는지를 설명하는 순서로 정리했습니다.

지원자 우상목  ·  2026년 10월  ·  첨부 코드 elice-infra/ (설계 파일, 설정 생성기, 시험 환경, Ansible)
요약SUMMARY

이 설계에서 가장 먼저 정한 원칙은 트래픽 종류마다 길을 따로 두는 것입니다. 손님의 웹 요청, 서버가 스토리지에 읽고 쓰는 데이터, 스토리지끼리의 복제, 관리자의 접속은 양도 다르고 문제가 생겼을 때의 영향도 다릅니다. 한 길에 섞어 두면 복제가 몰릴 때 서비스까지 느려지고, 한 곳이 뚫리면 다른 곳도 위험해집니다. 그래서 트래픽마다 연결과 네트워크를 나눴고, 서로 다른 구역 사이는 방화벽을 통해서만 오가게 했습니다.

설정은 손으로 만들지 않았습니다. 랙, 장비, 주소 같은 설계 값을 파일 하나(YAML)에 적고, 스위치 설정과 IP 표, 배선표는 모두 이 파일에서 자동으로 만들었습니다.

PART 1데이터가 다니는 길

먼저 전체 구조를 보고, 손님의 요청부터 장애가 났을 때의 우회까지 데이터가 실제로 지나가는 길을 따라갑니다.

PART 2구축 계획

그 길을 까는 데 필요한 장비와 배선, 서버 연결, 구역 나누기, 주소, 대역폭을 정리합니다.

PART 3운영 계획

그 길이 계속 잘 유지되도록 감시하고, 자동화하고, 고장에 대응하고, 늘려 가는 방법입니다.

PART 1데이터가 다니는 길전체 구조를 보고, 데이터가 실제로 지나가는 길을 따라갑니다
1-1전체 구조TOPOLOGY

서버 12대를 랙 3개에 나눴습니다. 랙마다 서버가 연결되는 스위치(리프) 2대를 두고, 모든 리프를 위쪽 스위치(스파인) 2대에 연결했습니다. 이런 구조를 스파인-리프라고 하며, 어느 서버에서 어느 서버로 가든 리프 → 스파인 → 리프 세 칸이면 도착합니다.

장비수량·위치하는 일
스파인2대 (R1, R3)모든 리프를 잇는 중심. 한 대가 꺼져도 나머지 한 대가 받습니다.
리프6대 (랙마다 2대)서버가 꽂히는 랙 맨 위 스위치. R1·R2의 리프는 방화벽도 연결합니다.
서버12대모든 연결을 같은 랙의 리프 두 대에 한 줄씩 꽂아, 리프 하나가 꺼져도 끊기지 않습니다.
방화벽2대 (R1, R2)인터넷과 내부, 내부 구역 사이를 오가는 유일한 문. 두 대가 한 쌍으로 서로를 대신합니다.
관리망 스위치3대 (랙마다 1대)서비스용 네트워크와 따로, 장비를 관리하는 연결만 모읍니다.

스파인과 방화벽, 컨트롤러는 일부러 서로 다른 랙에 나눠 뒀습니다. 랙 하나의 전원이 나가도 나머지 랙에서 서비스가 이어지게 하기 위해서입니다.

1-2트래픽 네 종류와 길 나누기FLOW MAP

이 네트워크에는 성격이 다른 트래픽 네 종류가 다닙니다. 아래 그림처럼 한 장에 겹쳐 보면, 서로 다른 트래픽이 같은 길을 다투지 않게 나뉘어 있습니다. 양이 많은 스토리지와 복제 트래픽은 방화벽을 거치지 않고 각자의 연결로 다니고, 방화벽은 구역을 넘나드는 트래픽(손님 요청, 관리 접속)만 지납니다.

트래픽어디서 어디로그래서 이렇게 나눴다
손님 요청인터넷 → 방화벽 → 워커밖에서 들어오므로 방화벽을 꼭 거치게 함
스토리지 읽기·쓰기워커 ↔ Ceph양이 많아 전용 연결을 따로 둠. 방화벽은 안 거침
스토리지 복제Ceph ↔ Ceph장애 때 폭주하므로 또 다른 연결로 분리. 밖으로 나가는 길 없음
관리 접속관리자 → 장비서비스망이 멈춰도 쓸 수 있게 관리망을 따로 둠

네트워크는 VRF(같은 스위치 안에서 라우팅 표를 아예 따로 쓰는 칸막이) 세 개로 나눴습니다. 서비스용(PROD), 스토리지용(STORAGE), 복제용(REPL)입니다. 칸막이가 다르면 같은 스위치를 지나도 서로의 길을 모릅니다.

1-3손님의 요청이 웹 서비스에 닿기까지CLIENT

사용자가 브라우저에서 엘리스 서비스를 열면, 요청은 공인 IP의 443번 포트로 들어옵니다. 그림의 주황색 번호를 따라가 보겠습니다.

#구간무슨 일이왜
인터넷 → 방화벽열어 둔 포트(80/443)인지 확인하고, 공인 주소를 내부 서비스 주소로 바꿔 넘김밖에 열린 문은 주소 하나, 포트 두 개뿐. 회선 2개, 방화벽 2대라 하나가 죽어도 문은 열려 있음
방화벽 → 리프서비스 주소가 어느 워커에 있는지 찾고, 다른 랙으로 보내기 위해 한 번 포장(VXLAN)함서비스가 떠 있는 워커들이 자기 위치를 알려 주므로, 여러 워커에 손님을 나눠 보낼 수 있음
리프 → 스파인포장 겉면의 목적지만 보고 전달. 스파인 두 대 중 하나로 나눠 보냄스파인은 단순한 고속도로. 한 대가 죽어도 다른 쪽으로 감
스파인 → 리프포장을 풀고 서비스 칸막이(PROD) 안에서 목적지 워커를 찾음칸막이가 달라 스토리지·복제 트래픽과 섞이지 않음
리프 → 워커서비스용 연결로 도착해 웹 서비스가 받음서비스 연결은 인터넷과 같은 크기(1500바이트)로 맞춰 큰 패킷이 버려지지 않게 함

응답은 같은 길을 거꾸로 갑니다. 방화벽은 들어온 연결을 기억하고 있어서, 나가는 응답을 다시 공인 주소로 바꿔 줍니다.

VXLAN: 랙이 달라도 같은 네트워크에 있는 것처럼 쓰려고, 원래 패킷을 한 번 더 감싸 보내는 방식입니다. 택배 상자를 큰 상자에 넣어 보내고 도착지에서 꺼내는 것과 비슷합니다.

1-4워커가 스토리지에서 데이터를 읽기까지STORAGE

웹 서비스가 사용자 데이터를 읽어야 합니다. 데이터는 네트워크 너머의 Ceph에 있습니다. R3의 wrk5가 R1의 ceph1에게 요청을 보냅니다. 그림 3의 보라색 알파벳 길입니다.

#구간무슨 일이왜
wrk5 → 리프서비스용이 아닌 스토리지 전용 연결로 나감손님 트래픽과 같은 줄을 다투지 않고, 방화벽도 거치지 않아 속도가 묶이지 않음
리프 → 스파인큰 패킷(9000바이트) 그대로 포장해 R1으로 보냄스토리지는 한 번에 크게 보내야 효율이 좋음. 스위치 사이는 포장해도 들어가는 크기(9216)로 맞춤
스파인 → 리프ceph1이 연결된 리프 두 대 중 한쪽으로리프 하나가 죽어도 다른 쪽으로 감
리프 → ceph1포장을 풀어 ceph1에 전달, 같은 길로 응답랙이 달라도 같은 네트워크처럼 동작
패킷 크기 설정이 한 곳이라도 어긋나면 작은 ping은 통과하는데 큰 데이터만 사라지는 장애가 생깁니다. 그래서 크기를 구간마다 정해 두고 따로 감시합니다(3-2). 실제로 막히기 쉬운 곳은 스파인이 아니라, 여러 Ceph가 한 워커로 동시에 응답하는 마지막 구간입니다. 이 구간은 스토리지 트래픽에 대역을 우선 보장해 다룹니다(2-5).
1-5데이터를 쓰면 일어나는 복제REPLICATION

사용자가 과제를 제출해 wrk5가 1MB를 씁니다. 데이터는 ceph1에 도착하지만 여기서 끝나지 않습니다.

#구간무슨 일이왜
wrk5 → ceph11-4와 같은 길로 1MB 도착-
ceph1 → 다른 랙의 Ceph 2대복제 전용 연결로 같은 데이터를 두 곳에 더 저장 → 2MB가 더 흐름쓰기 1이 복제 2를 부름. 손님 쪽 연결과 섞이면 서비스가 느려지므로 연결부터 분리
→ wrk5세 곳 모두 저장했다는 확인이 모여야 완료 응답복제가 느리면 손님이 느낌. 그래서 복제 연결도 넉넉하게(25G 두 줄)

이 길이 가장 붐비는 때는 Ceph 한 대가 고장 났을 때입니다. 남은 서버들이 잃어버린 복제본을 다시 만드느라 복제 연결이 꽉 찹니다. 복제 연결이 따로 있어서 이때도 손님 요청과 스토리지 읽기는 영향을 받지 않습니다. 복제용 칸막이(REPL)는 방화벽과도 연결하지 않았습니다. Ceph끼리만 쓰는 길이라 밖으로 나갈 이유가 없기 때문입니다.

1-6관리자가 장비에 접속하기까지MANAGEMENT

엔지니어가 집에서 서버를 점검해야 합니다. 관리 접속은 정해진 한 길로만 들어옵니다.

#구간무슨 일이왜
노트북 → VPN2단계 인증(MFA) 후 관리 구역에 들어옴관리망은 인터넷에서 직접 보이지 않음
VPN → 배스천모든 관리 접속은 접속용 서버(배스천) 한 곳을 거침누가 언제 무엇을 했는지 한곳에 기록
배스천 → 서버방화벽이 정한 포트(SSH, 모니터링 등)만 열어 줌관리 구역에서 서비스 구역으로는 필요한 것만
배스천 → 스위치스위치는 관리망 스위치를 통해 접속. 개인 계정으로 로그인하고 명령을 모두 기록서비스망이 통째로 멈춰도 관리망으로 들어가 고칠 수 있음
1-7막혀야 하는 패킷들BLOCKED

설계가 맞다면, 어떤 패킷은 목적지에 닿지 못해야 합니다. 구역을 나누고 방화벽을 둔 것이 실제로 무엇을 막는지 보겠습니다.

시도어디서 막히나왜
외부에서 서버 SSH(22번)로 접속방화벽열어 둔 목록에 없는 것은 전부 차단하고 기록
외부에서 스토리지로 직접 접근방화벽외부에서 스토리지·관리 구역으로 가는 허용 규칙이 없음
해킹당한 워커가 복제망으로방화벽서비스 칸막이에는 복제망으로 가는 길이 없고, 방화벽에도 그 길이 없음
설정 실수로 워커가 엉뚱한 주소를 알림리프리프는 워커에게서 서비스 주소만 받도록 걸러 냄
1-8길이 끊어졌을 때FAILURES

데이터가 오가는 도중에 장비가 고장 나면, 패킷은 이렇게 다른 길로 돕니다.

고장패킷에게 일어나는 일남는 영향
스파인 1대리프가 끊김을 알아채고 남은 스파인으로만 보냄속도는 절반, 서비스는 계속
리프 1대서버는 남은 리프 쪽 연결로만 주고받음그 랙 서버들의 속도가 절반
워커 1대그 워커로 가던 손님 요청이 다른 워커로남은 워커들이 나눠 받음
방화벽 1대, 회선 1개대기 중인 방화벽과 다른 회선이 이어받음수 초 ~ 수십 초 끊김
랙 하나 전체 정전네트워크와 Kubernetes는 남은 랙으로 계속 동작Ceph 4대가 2/1/1로 놓인 것이 약점. 복제본을 랙마다 하나씩 두어 데이터는 지키고, 다음 증설에서 2/2/2로 맞춤
PART 2구축 계획그 길을 실제로 까는 장비, 배선, 주소, 대역폭
2-1장비와 배선HARDWARE

3-1가용성과 장애 대응AVAILABILITY

고장이 났을 때 다른 길로 돌아가기까지 몇 초가 걸리는지가 핵심입니다. 같은 스파인-리프 구조를 직접 만들어 장애를 넣고, 0.2초마다 ping을 보내 끊긴 시간을 재 봤습니다.

케이블이 끊기는 고장은 0.2초면 다른 길로 돌았습니다. 더 위험한 것은 스파인이 꺼지지 않고 응답만 멈추는 고장이었습니다. 케이블은 살아 있어서 스위치들이 "상대가 죽었다"고 판단하기까지 9초를 기다렸고, 그동안 7.6~8.8초 동안 패킷이 사라졌습니다. 여기에 BFD(0.3초마다 서로 안부를 묻고, 세 번 연속 답이 없으면 끊긴 것으로 보는 기능)를 켜자 같은 고장이 0.8~1.2초로 줄었습니다. 그래서 이 설계는 스위치 사이 모든 연결에 BFD를 켭니다.

1. 서버 추가리프 포트 80% 사용설계 파일에 한 줄. 주소는 비워 둔 번호에서
2. 연결 늘리기리프-스파인 연결 70% 사용리프와 스파인 사이를 두 줄로
3. 랙 추가랙 전력 80% 사용리프 2대만 더함
4. 스파인 추가스파인 포트 부족스파인을 3~4대로 늘림

이렇게 쉽게 늘리려면 두 가지가 미리 돼 있어야 한다는 것을 시험 환경에서 배웠습니다.

  • 스위치끼리 연결에는 주소를 붙이지 않습니다(BGP unnumbered). 리프를 더할 때마다 연결용 주소를 계산할 필요가 없어집니다.
  • 여러 길에 고르게 나눠 보내게 합니다. 시험해 보니 기본 설정에서는 트래픽이 스파인 한쪽으로 크게 쏠렸고(3:42), 포트 번호까지 보도록 바꾸자 고르게 나뉘었습니다(21:23). 고르게 안 나뉘면 스파인을 늘려도 소용이 없습니다.
3-7GPU 노드 추가GPU

AI 학습에서는 GPU끼리 계산 결과를 끊임없이 주고받습니다. 한꺼번에 아주 많은 양이 오가고, 패킷 하나만 잃어도 전체 학습이 기다립니다. 지금까지의 트래픽과 성격이 완전히 다르므로, 같은 원칙대로 GPU 전용 네트워크를 하나 더 둡니다.

고려할 점내용
전용 네트워크GPU끼리만 다니는 빠른 네트워크(400G)를 따로 두고, 기존 네트워크는 관리와 데이터 공급, 추론 서비스에만 씁니다.
패킷 잃지 않기GPU 통신(RoCE)은 패킷 손실에 약합니다. 길이 막히기 전에 보내는 쪽 속도를 미리 줄이게(ECN) 하고, 정말 꽉 차면 잠깐 멈추게(PFC) 합니다. 작은 시험 환경에서 이 방식으로 손실이 약 50%에서 0으로, 지연이 19.8ms에서 1.3ms로 줄었습니다.
전력·냉각GPU 서버 한 대가 10kW 안팎이라 지금 랙(8kW)에 들어가지 않습니다. 전력이 큰 전용 랙이 필요하고, 네트워크보다 큰 비용입니다.
스토리지학습 데이터를 아주 빠르게 읽어야 해서 GPU 서버에 빠른 디스크(NVMe)를 두고, Ceph는 원본 보관에 씁니다.
추론만 한다면GPU끼리 주고받을 일이 적어 별도 네트워크 없이 기존 네트워크로 시작할 수 있습니다.
